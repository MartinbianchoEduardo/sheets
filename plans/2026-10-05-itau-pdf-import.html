01Purpose

Why we're doing this

Itaú no longer supplies the needed invoice as CSV. The app needs a reliable PDF source for the same current transactions.

★ North-star requirement

Within the approved current-year window, a PDF import must match the selected section totals and must never import a partial selected table.

02Problem

The problem we're solving

The invoices contain positioned text instead of a table data format. Two PDF generators split dates, amounts, and merchant text differently.

  • The merchant cell includes a first merchant line and a second category and location line.
  • The September invoice splits words, dates, and values into separate text items.
  • International charges and future installments appear near current transactions but are outside this feature.
  • A loose text parser can silently omit or merge rows while still producing valid-looking values.
03Solution

The shape of the solution

Use a pinned, lazy PDF.js package in the frontend. A focused Itaú parser rebuilds selected tables from text coordinates and emits the current raw import row shape.

  • Ignore page one. Scan later pages for supported section headings.
  • Read only Lançamentos: compras e saques and Lançamentos: produtos e serviços.
  • Use the current calendar year, the first merchant line, and the printed BRL value.
  • Discard the category and location line. Verify required private merchant titles through environment input without storing them in Git.
  • Compare each selected section sum with its printed section total before preview.
  • Send normalized rows to the existing preview route. Apply one selected configured card at confirmation.
04Requirements & scope boundaries

What's in, what's out

In scope: unencrypted text-based Itaú PDFs, the two selected current-transaction sections, current-year dates, first-line merchant titles, BRL values, a PDF card selector, section reconciliation, and the existing preview and confirmation flow. Approval includes a direct push to master and production Worker and Pages deployments after every required check passes. Out of scope: page-one data, international purchases, future installments, scanned PDFs, encrypted PDFs, OCR, external parsing services, database changes, and changes to CSV behavior. Duplicate rows keep the current warning behavior because this feature preserves the existing import method.

06Test strategy & validation

How we know it works

Use exact sample checks without committing the PDFs. October must produce 32 selected rows and 234360 cents. September must produce 16 selected rows and 172286 cents. Checks must read the two required private merchant titles from environment input, cover negative product or service credits, and exclude international and future installment rows. A changed amount must stop preview. The committed gastos-auth/src/import.test.js file must use Node built-in tests and a fake D1 environment for PDF cards, legacy CSV inference, impossible dates, and duplicate preview flags. The manual CSV regression input is `date,title,amount 2026-10-05,MERCHANT TEST,42.90`. It must preview as 05/10/2026, MERCHANT TEST, and R$ 42,90 from pasted text and a file. The final manual pass must cover current macOS Safari and iPhone Safari.

07Risks & dependencies

What could go wrong

PDF.js Safari support needs a real-device check. Itaú can change its layout, so the parser must stop on unknown anchors or total mismatch. Using the current year can assign December rows incorrectly when the user imports in January, but this behavior follows the approved requirement. First-line merchant text can contain unusual source spacing, so exact sample assertions guard the known formats. Duplicate warnings remain advisory to preserve the current import method. Private financial documents must never enter Git, logs, error reports, or network requests.
